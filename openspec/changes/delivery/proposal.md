## Why

The identity service and the family's site are built and tested locally, and nothing serves
them: `C:\meltemi` is not a Git repository, there is no GitHub repository, `meltemi.dev` still
answers from the IDE's GitHub Pages with its nameservers at Dynadot, `id.meltemi.dev` does not
resolve, and `@meltemi/identity`, which Meltemi Diagrams needs to install and deploy, is only a
`link:` on the owner's machine. The owner decided on 2026-10-20 to go to production, with two
rules: every piece of infrastructure configuration is Terraform (Cloudflare, the registrar,
GitHub, anything else that holds configuration), and everything runs as GitHub pipelines, never
from a machine. This is the delivery change decision 0001 reserved, and it goes first, because
Diagrams' delivery consumes its results: the zone, the identity service, the published package,
and the resources Terraform makes for it.

## What Changes

- **A public repository**, `https://github.com/askenaz-dev/meltemi-web`, Apache-2.0 (the licence
  the moved site files carry; the owner confirms it before the first push), with `LICENSE` at
  the root and an ignore file that keeps every secret, every build and Terraform's local files
  out.
- **The family's infrastructure as code, `packages/infra`.** One Terraform root with its state
  in an R2 bucket (locked with the backend's lock file), the Cloudflare provider and the GitHub
  provider, declaring: the zones `meltemi.dev` and `meltemi.page` (both registered at Dynadot) with their records; the two
  D1 databases and the R2 bucket of the family's Workers; the four Workers as entities
  (`meltemi-identity`, `meltemi-site`, `meltemi-diagrams-cloud`, `meltemi-diagrams-publish`)
  with no `workers.dev` and no preview address; their four Custom Domains; a Secrets Store with
  every Worker secret, the random ones generated by Terraform; two deploy tokens, one per
  product repository, minted by Terraform; and on GitHub the repositories `meltemi-web` and
  `meltemi-diagrams`, their `production` environments, their secrets (the deploy tokens, the
  npm and marketplace tokens) and the rules of `main`. Terraform also writes the ids each product
  needs (account, database, Secrets Store) as variables of its `production` environment, which
  the deploy workflows write into the Workers' configuration: nobody copies an id.
- **Pipelines for the infrastructure.** `infra-plan.yml` plans every pull request that touches
  `packages/infra` and writes the plan on it; `infra-apply.yml` applies every push to `main`,
  one at a time; `infra-drift.yml` plans weekly and opens an issue when the cloud differs from
  the code; `registrar.yml`, run by hand once, sets the nameservers of `meltemi.dev` at Dynadot
  and of `meltemi.page` to the ones their zones were given, through Dynadot's API (no Terraform
  provider exists for it).
- **Secrets from the Store, never from a machine.** The identity Worker reads its five secrets
  through Secrets Store bindings (`SESSION_PRIVATE_KEY`, `STATE_SECRET`, `GITHUB_CLIENT_SECRET`,
  `GOOGLE_CLIENT_SECRET`, `EVENTS_SECRET_DIAGRAMS`), with an adapter that also accepts the
  strings of `.dev.vars` in development, so `wrangler secret put` is never run anywhere.
- **`@meltemi/identity` published** to npm under the `meltemi` organisation, public, with
  provenance, from a release workflow on a version tag; the package stops being private.
- **Pipelines for the code.** `ci.yml` runs typecheck, lint, tests and the build on every push
  and pull request; `deploy.yml` applies the identity migrations and uploads the identity
  Worker's and the site Worker's code with `wrangler deploy` on every push to `main`, with the
  deploy token Terraform placed in the environment; `release.yml` publishes the package and a
  GitHub release on a `v<x.y.z>` tag.
- **The Workers' configuration.** Both `wrangler.jsonc` files name only what is the code's:
  the Worker's name, the bindings by the ids Terraform output, the Secrets Store bindings, the
  variables, `workers_dev: false` and `preview_urls: false`; no route and no Custom Domain, which
  are Terraform's.
- **The zone and the site swap.** Terraform creates the zone and its records with the apex on
  GitHub Pages; the registrar step moves the nameservers; the first `deploy.yml` run puts
  identity and the family site live together (the identity pages link `/privacy/` and
  `/terms/`, which only the family site has) once the apex records are removed from the code
  and the site's Custom Domain applied, retiring the IDE's Pages site as decision 0001 describes.
- **Docs and the owner's steps.** `README.md`, `docs/repositories.md`, `packages/infra/README.md`
  (the bootstrap, the pipelines, what Terraform cannot do), the package READMEs,
  `CONTRIBUTING.md` and decision 0004 record the delivery; the steps only a person can take
  (the bootstrap secrets, registering `meltemi.page`, the OAuth apps, the npm and marketplace
  accounts, the IDE repository's clean-up) are listed in order with the exact page or command.

## Capabilities

### New Capabilities

- `family-infrastructure`: the Terraform root, its state and providers, the resources it
  declares on Cloudflare and GitHub, the secrets and tokens it makes, its pipelines, the
  registrar step, and the Workers' secret bindings.
- `delivery-pipeline`: this repository's continuous integration, deployment and release
  workflows, the published identity package, and what the public repository holds.

### Modified Capabilities

None: the requirements of `identity-service` and `product-site` do not change; this change
configures, publishes and deploys what they specify, and the identity Worker's way of reading a
secret is an implementation detail of its configuration.

## Non-goals

- Meltemi Diagrams' delivery (its repository's contents, pipelines, the npm packages, the
  marketplaces, its Workers' code and bindings): the `delivery` change of
  `C:\development\dac`, which runs after this one and binds the ids this one outputs.
- The Meltemi IDE repository's own changes (removing `site/` and its Pages job, the tests and
  scripts that wrote into `site/media/`): the owner's steps there, as decision 0001 says.
- The owner tasks of `identity-service` (2.6, 2.8, 5.2) and `product-site` (4.2): they finish
  those changes, which are archived before this one.
- Terraform for what has no API or provider: registering a domain (Cloudflare Registrar and
  Dynadot register by hand), GitHub OAuth Apps, Google OAuth clients, npm and marketplace
  accounts and tokens; these are owner steps whose values enter the pipeline as secrets.
- Analytics, a staging environment, preview deployments, paid plans, `www.meltemi.dev`.

## Dependencies

New, with their licences: Terraform (BUSL-1.1, HashiCorp; 1.15 is installed on the owner's
machine, `hashicorp/setup-terraform` in the workflows), the Terraform providers
`cloudflare/cloudflare` 5.x (MPL-2.0), `integrations/github` 6.x (MIT) and `hashicorp/random`
3.x (MPL-2.0). `wrangler` and `@cloudflare/workers-types` (approved 2026-10-13) deploy and type
the Workers; `npm`, `gh` and the GitHub-hosted actions (`actions/checkout`,
`actions/setup-node`, `pnpm/action-setup`, `actions/github-script`) run in the workflows.
